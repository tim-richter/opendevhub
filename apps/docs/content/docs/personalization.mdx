Your team's `.devcontainer` holds what everyone needs. Personalization adds what only you use, such as a git workflow tool, a shell or your dotfiles. It is kept in opendevhub's `config.json` on your machine and never written to the repository.

Open **Settings → Personalization** to set it for every project. To add to it or turn it off for one project, open the project's settings (the gear in the project header) and go to **Personalization**.

## What you can add

- **Features**: [dev container Features](https://containers.dev/features) built into the image on top of the repository's own, passed to the dev container CLI as `--additional-features`. Only published features work (`ghcr.io/owner/repo/feature:1`, or an `https://` tarball). Local `./feature` folders don't, because they would have to be in the repository. Options are JSON, the same as in devcontainer.json.
- **Setup command**: a shell script run as the container's user once the container starts. It runs with `bash -l` when bash is installed and `sh -l` otherwise. It runs once per container and again after you change it. A marker in `~/.cache/opendevhub` records that it ran, and the marker is only written when the script succeeds, so a failed script runs again on the next start. A failure never stops the container. The output goes to the environment's log, prefixed with `personalize:`.
- **Dotfiles**: a repository the dev container CLI clones into each new container before it runs the repository's install script (`install.sh`, `setup.sh` and so on). This is the same mechanism that VS Code and Codespaces use. You can enter `owner/repo` for GitHub, or any git URL.

## How project settings combine

A project uses your global personalization and adds its own:

- For a feature that both list, the project's options win.
- Both setup commands run, the global one first.
- The project's dotfiles replace the global ones.

Turn off **Use your global personalization** for a project to give it only its own settings. The project page shows what its containers end up with.

## When changes apply

Features and dotfiles are part of how a container is created:

- **Project container:** rebuild it. Its Personalization settings say when it was created with other settings and offer a **Rebuild** button.
- **Task containers:** they are built from a base image. Your features are part of that image's key, so a new task container gets a fresh image. Rebuild an existing one to update it.

A changed setup command runs on the container's next start, with no rebuild.

## Example: Git Town for yourself only

Your team doesn't use Git Town, but you want it in every container. Add an install step as the global setup command. Follow [Git Town's installation guide](https://www.git-town.com/install) for the current release, for example:

```bash
# Example: check git-town.com/install for the current command
go install github.com/git-town/git-town/v21@latest
```

If a published dev container Feature for the tool exists, add it under **Features** instead. It is then built into the image once and cached, rather than installed on every new container.

The settings are stored like this:

```json
{
  "personalization": {
    "features": { "ghcr.io/devcontainers/features/github-cli:1": {} },
    "setupCommand": "go install github.com/git-town/git-town/v21@latest",
    "dotfiles": { "repository": "you/dotfiles" }
  },
  "projects": {
    "/src/app": {
      "personalization": { "inheritGlobal": false }
    }
  }
}
```

<Callout type="warn" title="It runs in the container">
  Setup commands and dotfiles install scripts run inside the project's
  container, with the container user's access to the workspace and to the
  ssh-agent opendevhub forwards. Only add scripts and repositories you trust.
</Callout>
